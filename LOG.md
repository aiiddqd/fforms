## 2026-09-12

- Блок «Приём заявок через API» на странице обзора переехал в «Частые вопросы» первым вопросом «Как быстро добавить приём сообщений через REST API?» (раскрыт по умолчанию); endpoint, состояние настроек, список типов и четыре примера с копированием — в ответе.
- Таксономия `fform_type` переименована в интерфейсе: «Типы заявок» → «Типы форм», «Тип заявки» → «Тип формы» — метки таксономии, пункт меню, колонка и фильтр списка ответов, блок «Дополнительно», настройки, экспорт, письмо и тексты ошибок REST; slug, коды ошибок и данные не менялись.
- Реализован RFC `headless-main-form`: встроенная главная форма (`Registry\Main_Form`, `key: main`, `source: builtin`) отдаётся в `GET /forms(/main)(/schema)`, ключ `main` зарезервирован за ней в `fforms_add_api_route()`.
- Добавлен маршрут `POST /fforms/v1/main` с плоским camelCase-payload: алиасы `formType`/`formId`/`form_type`/`form_id` (конфликт — 400), honeypot `_hp`, правило против пустых заявок 422 `fforms_empty_submission`; строгий контракт `/submit` не изменился.
- Общий пайплайн обработки отправки вынесен из `REST_Controller::submit()` в приватный `process()`; оба маршрута используют одни и те же rate limit, валидацию, создание entry, назначение типа и письма.
- Добавлена таксономия `fform_type`: нормализация и upsert по slug, лимит автосоздания (фильтр `fforms_max_form_types`, по умолчанию 50) с сохранением входного значения в `_fforms_form_type_raw`, строгий режим в настройках.
- Форма и тип связаны в обе стороны: публикация CPT-формы создаёт термин со slug = `post_name` и метой `_fforms_form_id`, переименование формы меняет только `name`, удаление формы термин сохраняет. Slug термина стал третьим путём резолва в `Form_Locator` — стабильный строковый ключ формы вместо post ID.
- Данные вне схемы сохраняются отдельно от валидированных: меты `_fforms_custom` (20 скалярных ключей), `_fforms_meta` (глубина 3, 8 KiB), `_fforms_ref`, `_fforms_user_id`; неизвестные ключи верхнего уровня уходят в `customFields`, а не теряются.
- Админка: колонка и фильтр по типу заявки в списке ответов, блок «Дополнительно» на экране ответа, экран «Типы заявок» в меню FForms, переход форма ↔ заявки в обе стороны.
- `GET /entries` получил фильтр `form_type`; CSV — колонки `form_type`, `ref`, `user_id`, `custom_fields`, `meta` и фильтр экспорта по типу; письмо уведомления — блок с типом и данными вне схемы.
- Настройки дополнены разрешёнными origins главной формы, получателями её уведомлений и строгим режимом типов; CORS-ветка `/main` использует этот список независимо от того, какую форму адресовал payload.
- Обзор переехал на `admin.php?page=fforms-dashboard` с редиректом со старого адреса; добавлен блок «Приём заявок через API» с реальным URL маршрута, состоянием настроек, списком типов и четырьмя примерами запросов.
- Вложения вынесены из `headless-main-form` в отдельный RFC `main-form-attachments`: на `/main` они отклоняются с 400 (`fforms_attachments_require_multipart` для JSON, `fforms_attachments_disabled` для multipart) и на диск ничего не пишется.
- Таксономия регистрируется с `show_in_menu => false` и одним явным пунктом меню: ядро иначе добавляет экран отдельно для каждого связанного CPT, и «Типы заявок» дублировались.
- Колонка таксономии сохраняется в `Post_Types::entry_columns()`: фильтр полностью пересобирал набор колонок и отбрасывал сгенерированный ядром `taxonomy-fform_type`.
- Базовая и headless-спецификации дополнены главной формой, таксономией `fform_type`, порядком резолва формы, новыми метами ответа, маршрутом `/main` и CORS для него.
- Зафиксировано ограничение проверки: `npm run lint:js` и `npm run lint:css` падают с тем же числом ошибок на чистом дереве (ignore-пути обходят `node_modules`/`build`); `php -l` и `npm run build` проходят.
- RFC `headless-main-form`: встроенная главная zero-config форма (`key: main`), лояльный маршрут `POST /fforms/v1/main` с плоским payload, тип заявки как таксономия `fform_type` с двусторонней связью «форма ↔ термин», колонкой и фильтром в списке ответов, данные вне схемы, вложения и переезд обзора на `admin.php?page=fforms-dashboard` с примерами запросов — черновик доведён до полного шаблона RFC.
- Голый embed-документ сбрасывает `height`/`min-height`/`overflow` у `html` и `body`: стили темы делали body скролл-контейнером во фрейме, из-за чего документ сообщал высоту фрейма вместо своей и форма обрезалась со внутренней полосой прокрутки.
- Исправлена обрезка формы во фрейме: высота измеряется по контенту, а не по `documentElement`, повторно отправляется, пока фрейм ей не соответствует, и ставится inline-стилем поверх CSS темы; убран `scrolling="no"`, чтобы ошибка измерения не резала контент молча.
- Публичная форма получила «голый» режим `?fforms_embed=1` — документ без шапки, подвала и админ-бара для вставки во фрейм; сниппеты iframe и js-script теперь ведут на него, а обычная ссылка `/forms/{id}` осталась полной страницей для шаринга.
- Точный URL фрейма передаётся в `data-fforms-src`, чтобы скрипт не угадывал слеш в permalink и не ловил лишний 301.
- Базовая спецификация дополнена разделом 7.2 про внешнюю вставку формы через iframe и js-script.
- В боковой панели формы собраны все точки вставки: шорткод, публичная ссылка, iframe и js-script; iframe и js-script показываются только для опубликованной формы в режиме «Share via URL».
- Публичная страница формы во фрейме сообщает свою высоту родителю через `postMessage` (`assets/public-form-frame.js`); вне фрейма репортер не активируется.
- Добавлен `assets/embed.js` — вставка формы на сторонний сайт: скрипт подставляет iframe публичной страницы формы и подгоняет высоту по `postMessage`.
- Базовая спецификация дополнена разделом 7.1 про шорткод `[fform id=123]`, политику недоступной формы и подключение ассетов.
- Отлажен сквозной сценарий вставки: блок и шорткод на обычной странице дают одинаковую разметку, уникальные DOM id, 201 на отправке, 422 с ошибкой поля и ложный успех на honeypot.
- Зафиксировано, что `/services/wwdb` рендерится шаблоном темы `code-driven` в обход `the_content()`, поэтому сценарий прогнан на обычной странице; исходное содержимое страницы восстановлено.
- Сообщение о недоступной форме стало настраиваемым: `Form_Renderer::render_form()` принимает `$unavailable_notice`, общая политика «гость — пустота, редактор — сообщение» вынесена в `editor_notice()`.
- Содержимое формы теперь разворачивает шорткоды внутри окна guard'а рекурсии, поэтому `[fform id=X]` внутри формы X отдаёт сообщение о циклической ссылке вместо литерального текста.
- В боковую панель формы добавлено поле с готовым шорткодом `[fform id=<ID>]` для опубликованной формы режимов `block`/`public`.
- Добавлен шорткод `[fform id=123]` (`includes/class-shortcode.php`) как тонкая обёртка над `Form_Renderer::render_form()` с ранним и поздним подключением ассетов формы.
- Удалены мёртвые legacy-ассеты `assets/block-editor.js`, `assets/view.js`, `assets/view.css`, не подключавшиеся ни из одного PHP-файла.
- Добавлен RFC `docs/rfc/form-embed-block-and-shortcode.md`: вставка формы блоком и шорткодом `[fform id=123]`, отладочный сценарий на живой странице, удаление мёртвых legacy-ассетов.
