# RFC: FForms как backend для headless CMS через REST API

## туду
- [x] broke link Settings in wp admin - http://localhost:8890/wp-admin/fforms-settings

## Вводные

Сегодня форма существует только как запись CPT `fform`, а весь submit-путь завязан на числовой `form_id`. Для headless-фронтенда (AstroJS) это неудобно: форму надо создавать руками в админке, а ключ формы в коде фронтенда — это post ID, который меняется между окружениями. Предлагается добавить программную регистрацию форм: `fforms_add_api_route( $key, $args )` объявляет форму в PHP, она становится доступной по строковому ключу через `fforms/v1` и принимает заявки с внешнего домена.

## Назначение и цели

- Дать возможность описывать форму в коде темы/плагина: имя, ключ, набор полей — без записи в БД.
- Сделать строковый ключ формы стабильным идентификатором в REST-контракте, чтобы фронтенд не зависел от post ID и одинаково работал на dev/stage/prod.
- Позволить внешнему домену отправлять заявки: per-form allowlist origins и корректный CORS-preflight.
- Сохранить единый путь обработки: та же валидация, honeypot, rate limit, хранение entries, письма и `fforms_entry_created`.

Заинтересованные стороны: разработчики headless-фронтендов, интеграторы FForms, ревьюеры REST-контракта и безопасности.

Вне объёма: редактирование code-форм в админке, рендер code-формы блоком `fforms/form`, программное удаление форм, per-form токены и подписи запросов, версия `v2` REST API.

## Предпосылки
- ок модель есть и даже констурктор форм
- но надо чтобы формы можно было добавлять программно, типа fforms_add_api_route(...)
- суть в том что минимально надо указать какие поля нужны для формы и ее название и ключ
    - название - человеко понятное

- цель - после регистрации появляется роут для работы с формой через REST API - прием заявок с фронтенда типа AstroJS

## Составляющие и особенности

### 1. Публичная функция регистрации

```php
add_action( 'fforms_register_forms', function () {
    fforms_add_api_route( 'contact_astro', array(
        'title'           => 'Контакт (Astro)',
        'fields'          => array(
            array( 'name' => 'email', 'label' => 'Email', 'type' => 'email', 'required' => true ),
            array( 'name' => 'message', 'label' => 'Сообщение', 'type' => 'textarea', 'required' => true ),
        ),
        'origins'         => array( 'https://example.com' ),
        'success_message' => 'Спасибо!',
        'notifications'   => array( 'enabled' => true, 'to' => 'sales@example.com', 'subject' => '' ),
    ) );
} );
```

Обязательны только `title` и `fields`; остальное имеет значения по умолчанию. Возвращает `true` или `WP_Error`. Действие `fforms_register_forms` вызывается на `init` с приоритетом 5 — до `rest_api_init`, поэтому реестр гарантированно заполнен к моменту регистрации маршрутов.

Ключ: `sanitize_key`, паттерн `^[a-z0-9_]{1,32}$`. Повторная регистрация того же ключа — `WP_Error`, первая регистрация побеждает. `fields` проходят через существующий `Schema::normalize()`, поэтому набор типов, лимиты (50 полей, 100 опций, `max_length`) и правила валидации совпадают с CPT-формами. Пустая или невалидная схема при регистрации — ошибка, а не подстановка дефолтных полей.

### 2. Реестр и единый способ адресовать форму

`FForms\Registry\Code_Forms` — статический реестр в памяти (`register`, `get`, `exists`, `all`), без записей в БД: код остаётся единственным источником правды.

Чтобы не дублировать ветвления по всему плагину, вводится value object `FForms\Form_Ref` со свойствами `post_id`, `key`, `title`, `schema`, `success_message`, `origins`, конфигурацией писем и `source` (`post` | `code`). Резолвер `FForms\Form_Locator::resolve( int|string $ref ): Form_Ref|WP_Error` возвращает его для опубликованной CPT-формы (по ID) или для зарегистрированной code-формы (по ключу). Весь код ниже работает только с `Form_Ref`, а не с post meta напрямую.

### 3. REST-контракт

- `POST /fforms/v1/submit` — остаётся единственным эндпоинтом отправки. `form_id` перестаёт быть обязательным, добавляется `form_key` (string). Ровно один из двух обязателен, иначе 400 `fforms_form_ref_required`. Дальнейшая обработка не меняется: honeypot, rate limit, валидация, entry, письма, action.
- `GET /fforms/v1/forms/(?P<key>[a-z0-9_]+)` и `/schema` — чтение code-формы. Регистрируются после существующих числовых маршрутов, поэтому числовые ID продолжают попадать в прежний обработчик.
- `GET /fforms/v1/forms` — отдаёт CPT- и code-формы вместе. В payload формы добавляются `key` (для CPT — `null`) и `source`.
- `GET /fforms/v1/entries` — новый фильтр `form_key` рядом с `form_id`.

Rate limit считается по паре «ссылка на форму + IP», где ссылка — post ID либо ключ.

### 4. Entries, письма, админка

Entry code-формы сохраняет `_fforms_form_key`, а `_fforms_form_id` остаётся `0`. Список ответов, колонки админки, экран просмотра и CSV-экспорт получают название формы через `Form_Locator`, а не через `get_the_title()`. В CSV добавляется колонка `form_key`; в селекте экспорта появляются code-формы. Если entry ссылается на ключ, которого больше нет в коде, показывается сам ключ — данные не теряются.

`Notifications::send()` принимает `Form_Ref` вместо `form_id` и берёт настройки писем из него. Глобальный тумблер почты в `Settings` продолжает действовать: он остаётся общим предохранителем и для code-форм.

### 5. CORS

Плагин отдаёт CORS-заголовки только для namespace `fforms/v1` и только когда заголовок `Origin` точно совпадает (схема + хост + порт) с элементом `origins` целевой формы. Wildcard и `Access-Control-Allow-Credentials` не поддерживаются. Preflight `OPTIONS` обрабатывается для submit-маршрута с `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Allow-Headers: Content-Type` и `Max-Age: 600`. Итоговый список расширяется фильтром `fforms_allowed_origins`. Форма без `origins` ведёт себя как сейчас — CORS остаётся заботой сайта.

## Критерии приемки (checklist)

- [x] `fforms_add_api_route()` регистрирует форму; повторный ключ, невалидный ключ и пустые `fields` возвращают `WP_Error` и не ломают загрузку сайта.
- [x] `GET /fforms/v1/forms` содержит и CPT-, и code-формы; у каждой есть `key` и `source`.
- [x] `GET /fforms/v1/forms/{key}` и `/schema` отдают схему code-формы; числовой `GET /forms/{id}` работает как раньше.
- [x] `POST /submit` с `form_key` создаёт entry; ответ 201 с `entry_id` и сообщением формы.
- [x] `POST /submit` без `form_id` и без `form_key` возвращает 400; с несуществующим ключом — 404.
- [x] Валидация, honeypot (200 без entry), rate limit 429 и лимит размера тела работают для code-форм так же, как для CPT-форм.
- [x] Entry code-формы виден в админке и в `GET /entries?form_key=...`, показывает человекочитаемое название и выгружается в CSV с колонкой `form_key`.
- [x] Письмо и автоответ по code-форме уходят при включённых настройках и не уходят при выключенном глобальном тумблере.
- [x] Запрос с разрешённого origin получает `Access-Control-Allow-Origin`; с чужого — нет; `OPTIONS` возвращает 204 с корректными заголовками.
- [x] Существующий submit по `form_id` из блока `fforms/form` не сломан; `php -l`, `npm run lint:js`, `npm run lint:css` проходят. (`lint:css` сообщает только о ранее существовавших ошибках в `docs/rfc/archive/mvp/jetpack/jetpack_vendor/**` — не связано с этим PR.)
- [x] Тестовые формы и параметры не добавляются кодом или конфигурацией FForms: E2E создаёт CPT-формы через wp-admin. Проверка программно зарегистрированной формы выполняется в интеграционных тестах потребляющей темы/плагина.
- [x] `docs/specs/api-route-headless-cms-mode.md` дополнен разделом о code-формах и обновлённым REST-контрактом.

## Дорожная карта

1. Реестр `Code_Forms`, `Form_Ref`, `Form_Locator`, функция `fforms_add_api_route()` и хук `fforms_register_forms`.
2. Перевод `REST_Controller::submit()` и read-маршрутов на `Form_Ref`; поддержка `form_key`.
3. Рефакторинг `Notifications` на `Form_Ref` и сохранение `_fforms_form_key` у entry.
4. Админка, фильтр `form_key` в `/entries` и CSV-экспорт.
5. CORS-слой с per-form allowlist и preflight.
6. Пример интеграции с AstroJS в документации и ручная проверка сценариев из чек-листа.

Шаги 1–2 блокируют всё остальное; 3–5 независимы между собой.

## Итого и рекомендации

Рекомендуется не строить параллельный «headless API», а расширить существующий `fforms/v1`: добавить строковый ключ как второй способ адресовать форму и абстракцию `Form_Ref`, через которую одинаково проходят CPT- и code-формы. Это даёт headless-сценарий из «Предпосылок» минимальным изменением поверхности API и без риска для уже работающего блока.
