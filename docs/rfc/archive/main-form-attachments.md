# RFC: main form attachments — приём файлов на `POST /fforms/v1/main`

## Вводные

Маршрут `POST /fforms/v1/main` (см. `headless-main-form.md`) сегодня отклоняет любые файлы: `attachments` в JSON-теле — 400 `fforms_attachments_require_multipart`, `multipart/form-data` с файлами — 400 `fforms_attachments_disabled`. Этот RFC заменяет контракт отказа на рабочий приём вложений. Раздел вынесен из `headless-main-form.md` отдельно, потому что анонимная загрузка файлов — самостоятельная поверхность атаки: проверка типа по содержимому, хранение вне media library, защищённая выдача и удаление вместе с entry.

## Назначение и цели

- Дать headless-фронтенду возможность приложить к заявке файл (резюме, бриф, скан) без создания attachment-записей и без публичного URL.
- Не открывать анонимную загрузку в media library и не расширять поверхность атаки по умолчанию.
- Не писать на диск ничего до успешной валидации и создания entry.

Заинтересованные стороны: разработчики headless-фронтендов, ревьюеры безопасности, администраторы сайтов с ограниченным дисковым пространством.

## Составляющие и особенности

### 1. Тумблер в настройках

«Разрешить вложения» — **по умолчанию выключен**. При выключенном тумблере поведение остаётся сегодняшним: 400 `fforms_attachments_disabled`. Zero-config относится к созданию формы, не к загрузке файлов: хранение пользовательских файлов требует осознанного решения администратора (`base.md` §10).

### 2. Приём

Файлы принимаются только в `multipart/form-data` как `attachments[]`; `attachments` в JSON-теле — 400 `fforms_attachments_require_multipart`.

- Лимиты: ≤ 3 файлов, ≤ 5 MiB каждый; общий лимит тела для этого маршрута — отдельный фильтр `fforms_main_form_max_upload_bytes` (по умолчанию 16 MiB), поскольку `fforms_max_request_bytes` (256 KiB) остаётся лимитом JSON-запросов.
- Тип проверяется `wp_check_filetype_and_ext()` и `finfo` по содержимому, а не по расширению. Allowlist: pdf, png, jpg/jpeg, webp, txt, csv, docx, xlsx. Исполняемые и активные типы (php, phtml, html, js, svg) запрещены всегда, фильтром типов их расширить нельзя.

### 3. Хранение

Вне media library: `uploads/fforms-private/<Y>/<m>/` с `index.html`, `.htaccess` (deny from all) и случайным именем файла. Публичного URL у файла нет; attachment-записи не создаются. Метаданные (оригинальное имя, MIME, размер, путь) хранятся в мете entry `_fforms_attachments`.

Файлы записываются на диск **после** успешной валидации и создания entry — невалидные и rate-limited запросы не оставляют мусора. Удаление entry (`before_delete_post`) удаляет его файлы.

### 4. Выдача

`GET /fforms/v1/entries/{id}/attachments/{index}` с `manage_options`, отдаёт файл потоком с `Content-Disposition: attachment`. Ссылки на этот маршрут идут в письмо уведомления и на экран entry; сами файлы к письму не прикрепляются.

### 5. Админка и экспорт

Список вложений в блоке «Дополнительно» на экране entry; CSV получает колонку `attachments` с именами файлов.

### 6. Вне объёма

Приём вложений на существующем `/submit`, загрузка в media library, превью изображений в админке, антивирусная проверка, retention-политика для файлов отдельно от entry.

## Критерии приемки (checklist)

- [ ] При выключенном тумблере `multipart`-запрос с файлом возвращает 400 `fforms_attachments_disabled`; `attachments` в JSON-теле — 400 `fforms_attachments_require_multipart`.
- [ ] При включённом тумблере pdf и png сохраняются, entry получает мету `_fforms_attachments` с оригинальным именем, MIME и размером.
- [ ] `.php` и `.svg` отклоняются, в том числе переименованные в `.pdf` (проверка по содержимому).
- [ ] 4-й файл и файл больше 5 MiB отклоняются; тело больше `fforms_main_form_max_upload_bytes` даёт 413.
- [ ] Файл недоступен по прямому URL в `uploads/`; каталог содержит `index.html` и `.htaccess`.
- [ ] `GET /entries/{id}/attachments/{index}` отдаёт файл администратору и отказывает анонимному запросу.
- [ ] Невалидный и rate-limited запрос не оставляет файлов на диске.
- [ ] Удаление entry удаляет его файлы с диска.
- [ ] Список вложений виден на экране entry, ссылки есть в письме уведомления, CSV содержит колонку `attachments`.
- [ ] `php -l`, `npm run lint:js`, `npm run lint:css`, `npm run build` проходят; `docs/specs/` и `LOG.md` обновлены.

## Дорожная карта

1. Настройка «Разрешить вложения» и снятие контракта отказа с `/main`.
2. Multipart-ветка маршрута: разбор `attachments[]`, лимиты по количеству и размеру.
3. Проверка типов по содержимому (`finfo` + `wp_check_filetype_and_ext()`), жёсткий запрет активных типов.
4. Приватное хранилище: каталог, `.htaccess`/`index.html`, случайные имена, мета `_fforms_attachments`.
5. Защищённая выдача `GET /entries/{id}/attachments/{index}`.
6. Удаление файлов вместе с entry (`before_delete_post`).
7. Админка, письмо и CSV.
8. Документация и ручная проверка чек-листа.

## Предпосылки

Раздел §5 исходного RFC `headless-main-form.md`, вынесенный отдельно по решению от 2026-09-12, чтобы не блокировать главную форму объёмом и рисками загрузки файлов.

## Итого и рекомендации

Вложения строятся «приватно по умолчанию»: нет тумблера — нет загрузки; есть тумблер — файлы лежат вне media library, без публичного URL, и отдаются только по capability. Проверка типа идёт по содержимому, а не по расширению, и allowlist нельзя расширить до активных типов фильтром.

## Открытые вопросы

- Нужна ли retention-политика для файлов отдельно от entry (удалять файлы старше N дней, сохраняя заявку).
- Нужен ли лимит суммарного объёма хранилища и что делать при его исчерпании.
- Стоит ли давать фильтр для расширения allowlist безопасными типами (zip, odt) или оставить список фиксированным.
