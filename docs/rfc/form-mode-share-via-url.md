# RFC: Режим формы — «Share via URL» как третье значение вместо отдельной группы «Публичная форма»

## Вводные

Сейчас в боковой панели формы независимо друг от друга живут SelectControl «Режим формы» (`block`/`headless`, meta `_fforms_mode`) и отдельная панель «Публичная форма» с тумблером «Открыть форму по публичной ссылке» (meta `_fforms_public`). Комбинация `headless` + `public=true` не работает: публичная страница показывает редакторский плейсхолдер вместо формы. Решение — убрать отдельную панель и добавить в тот же SelectControl третье значение **«Share via URL»**, которое семантически равно `block` + включённая публичная ссылка. Тумблер и его панель исчезают, `_fforms_mode` становится трёхзначным.

## Назначение и цели

Два независимых переключателя создают невалидное состояние (headless+public), которое ничем не предотвращается в UI и приводит к «сломанной» публичной странице — редактор не может понять, почему форма не открывается по ссылке. Цель — свести режим формы к одному явному выбору из трёх взаимоисключающих сценариев использования, устранить саму возможность невалидной комбинации и упростить панель настроек (одно поле вместо поля + группы с тумблером).

Заинтересованные стороны: администраторы, создающие формы в wp-admin; разработчики headless-фронтендов (их REST-контракт не меняется); ревьюеры UX админки. Опирается на предпосылки и терминологию `docs/rfc/form-creation-mode-block-vs-headless.md` (тот RFC уже в статусе `implementing`, этот документ его не редактирует, а расширяет).

Вне объёма: генерация готового `<iframe>`-сниппета для вставки на сторонний сайт — такой функции в кодовой базе нет и сейчас, «share via url» лишь называет практику (владелец сайта сам решает, вставлять ли публичный URL в iframe). Не меняется REST-контракт (`GET /forms`, `/schema`, `POST /submit` и так уже полностью публичны независимо от режима — `docs/specs/base.md`).

## Составляющие и особенности

1. **Модель данных.** `_fforms_mode` расширяется до `'block' | 'headless' | 'public'` (дефолт `'block'`). Значение `'public'` идентично `'block'` во всех местах кода, которые сегодня проверяют `mode === 'block'`/embeddable-логику (рендер как блок, доступность в пикере `ref`) — отличие только в том, что `Public_Form::is_enabled()` включает публичный `/forms/{id}/` URL. Отдельная meta `_fforms_public` выводится из употребления как поле, управляемое UI: `Public_Form::is_enabled()` переходит на проверку `Post_Types::form_mode( $id ) === 'public'` вместо чтения `_fforms_public`.

2. **Одноразовая миграция существующих форм** (например, хук на `admin_init`/upgrade-роутина по номеру версии опции плагина):
   - `mode=block, public=true` → `mode='public'` (полноценно рабочая комбинация, переносим как есть, ссылка продолжает работать без изменений URL);
   - `mode=block, public=false` → `mode='block'`, без изменений;
   - `mode=headless, public=true` → остаётся `mode='headless'`; сам факт `public=true` никогда не давал рабочую публичную страницу (см. «Предпосылки»), поэтому потери функциональности нет — это устранение уже сломанного состояния;
   - После миграции meta `_fforms_public` удаляется у всех форм (`delete_post_meta`) и снимается с регистрации (`register_post_meta` для `_fforms_public` убирается из `Post_Types::register_meta()`), чтобы не оставлять «мёртвое» REST-поле.

3. **UI.** `assets/form-settings-sidebar.js`: `SelectControl` «Режим формы» получает третий `option` — «Share via URL» (лейбл на русском в панели, например «По ссылке»/«Share via URL» — финальная формулировка на усмотрение реализации, единообразно с двумя другими лейблами). Панель `PluginDocumentSettingPanel(name: 'public-form')` и её `ToggleControl` удаляются целиком. Блок с публичным URL (текущий `form-settings-sidebar.js:334-378`, вывод `publicFormUrl` при `status === 'publish'`) переносится под условие `mode === 'public' && status === 'publish'` в ту же панель «Настройки формы», сразу под селектом режима — то есть визуально там же, где сейчас на макете показана ссылка, просто без отдельной секции.

4. **`updateMode()` на клиенте.** Переключение в `'public'` не требует конвертации блоков (это тот же `block`-шаблон), в отличие от перехода в/из `'headless'`, где сегодня выполняется перенос полей в/из `fforms/headless-schema`. Переход `headless → public` и `public → headless` проходит те же преобразования блоков, что и `headless ↔ block` сегодня (поскольку `public` рендерится как `block`).

5. **PHP.** `sanitize_form_mode()` (`includes/class-post-types.php:121-123`) допускает третье значение `'public'` в белом списке. `Post_Types::form_mode()` не меняет приоритет детекции по блоку `fforms/headless-schema` — присутствие этого блока по-прежнему форсирует `headless` независимо от meta (существующий инвариант сохраняется). `Public_Form::is_enabled()` (`includes/class-public-form.php:47-49`) читает `_fforms_mode === 'public'` вместо `_fforms_public`. REST-поле `mode` в ответах `GET /forms`, `/forms/{id}` теперь может возвращать три значения — потребители, фильтрующие по `mode === 'headless'` (пикер `ref` в инспекторе блока), не меняют логику: `public` для них ведёт себя как `block` (уже отфильтровывается только `headless`, доп. правок не требуется).

## Критерии приемки (checklist)

- [x] `_fforms_mode` принимает и валидирует три значения: `block`, `headless`, `public`; неизвестное значение откатывается на `block`.
- [x] В боковой панели один SelectControl с тремя опциями; отдельная панель/группа «Публичная форма» и её тумблер удалены из UI.
- [x] Выбор «Share via URL» рендерит форму как обычный блок на странице (как `block`) и одновременно открывает `/forms/{id}/` без авторизации при `status === 'publish'`.
- [x] Выбор «Headless API» не показывает и не позволяет включить публичную ссылку (поля для этого больше нет).
- [x] Публичная ссылка в панели отображается сразу под селектом режима при `mode === 'public'` и `status === 'publish'`, в остальных режимах — не отображается.
- [x] Одноразовая миграция переносит `block+public=true` → `public`, оставляет `block+public=false` без изменений, приводит `headless+public=true` к `headless` (без потери реально работавшей функциональности, так как эта комбинация ранее не рендерила форму).
- [x] Meta `_fforms_public` удалена у всех форм после миграции и снята с регистрации в `Post_Types::register_meta()`.
- [x] `GET /fforms/v1/forms` и `GET /fforms/v1/forms/{id}` возвращают `mode` со значением `public` для соответствующих форм; пикер формы (`ref`) в инспекторе блока `fforms/form` по-прежнему исключает только `headless`-формы и предлагает `public`-формы к выбору.
- [x] `POST /fforms/v1/submit` и чтение схемы работают одинаково для всех трёх режимов — REST-контракт не меняется.
- [x] `php -l`, `npm run lint:js`, `npm run build` проходят; `docs/specs/base.md` дополнен описанием третьего значения `_fforms_mode` и поведения `Public_Form` (сейчас там не задокументировано).

## Дорожная карта

1. Расширить `_fforms_mode` до трёх значений в `sanitize_form_mode()`; `Public_Form::is_enabled()` переходит на чтение `_fforms_mode`.
2. Написать и подключить одноразовую миграцию существующих форм (`block+public` → `public`; удаление `_fforms_public`).
3. Обновить `assets/form-settings-sidebar.js`: третья опция в селекте, удаление панели «Публичная форма», перенос блока с URL под условие `mode === 'public'`.
4. Убедиться, что пикер `ref` и REST-ответы (`mode`) корректно обрабатывают `public` как «встраиваемый» режим наравне с `block`.
5. Обновить `docs/specs/base.md` (раздел про `_fforms_mode`/`Public_Form`), прогнать чек-лист вручную.

Шаг 1 блокирует шаг 2; шаг 3 зависит от шага 1 (использует то же множество значений), но не от шага 2 (миграция — серверная, не влияет на форму JS); шаг 4 можно вести параллельно с шагом 3.

## Итого и рекомендации

Не вводить отдельное поле для «публичности» — трёхзначный `_fforms_mode` полностью описывает три взаимоисключающих сценария использования формы и на сервере, и в UI. Это устраняет невалидную комбинацию `headless+public`, не добавляя нового формата хранения или REST-пути: `public` технически обрабатывается как `block` везде, кроме проверки в `Public_Form`. Миграция односторонняя и не теряет ранее рабочую функциональность, так как единственная схлопываемая комбинация (`headless+public`) никогда не рендерила форму.

## Опциональные разделы

### Открытые вопросы

- Финальная русская формулировка третьего пункта в селекте («Share via URL», «По ссылке», «Публичная форма» как название пункта) — на усмотрение реализации/дизайн-ревью, в макете пользователя фигурировало английское «Share via URL».
- Нужно ли в будущем добавить генерацию `<iframe>`-сниппета с примером кода рядом с публичной ссылкой — сейчас сознательно вне объёма, зафиксировано как возможное расширение.
