# RFC: Аккуратные базовые стили формы по умолчанию

## Вводные

Форма «из коробки» выглядит неопрятно: в редакторе поля слипаются рамками, кнопка примыкает к `textarea`, иерархия отступов не читается. Причина не в отсутствии дизайна, а в трёх конкретных дефектах разметки и в наборе дефолтов CSS-переменных, подобранных «в нейтральный ноль». Предлагаем починить дефекты и пересобрать шкалу значений по умолчанию — без собственной дизайн-системы, без роста специфичности и без изменения контракта темизации из `docs/specs/theming.md`.

## Назначение и цели

Добавил форму — и сразу можно работать: нейтрально, опрятно, с читаемой иерархией, без правки `theme.json` и без пользовательского CSS. Тема по-прежнему главнее плагина: всё остаётся на `:where()` и на публичных переменных, Global Styles выигрывают всегда.

Заинтересованные стороны: редакторы форм, владельцы сайтов без дизайнера, авторы тем, ревьюеры FForms.

Вне объёма: собственная палитра и дизайн-система, block style variations, адаптивные design controls, изменение REST-контракта и валидации.

## Диагноз

1. **В конструкторе нет контейнера с `gap`.** `EditBuilder` ([edit-builder.js](src/blocks/form/edit-builder.js)) кладёт inner blocks прямо в `useBlockProps()` → `.wp-block-fforms-form`. Правило `:where(.fforms-form, .fforms-fields, …) { display: grid; gap: … }` из [style.scss](src/blocks/form/style.scss) не совпадает ни с чем, потому что классов `.fforms-form`/`.fforms-fields` в редакторе нет — их создаёт только серверный `render_shell()`. Отсюда `gap: 0` на скриншоте: рамки соседних полей соприкасаются, кнопка прижата к сообщению.
2. **Разметка редактора и фронта различается.** В редакторе внутри `.fforms-field` есть ещё одна grid-обёртка `.fforms-field-preview` ([field.js](src/blocks/field.js)); на фронте `label`/`control`/`error` — прямые потомки `.fforms-field`. Два разных дерева → два разных результата.
3. **Пустой `<p class="fforms-field-error">` занимает место.** Он всегда в DOM и всегда grid item, поэтому под каждым контролом висит «мёртвый» `--fforms-field-gap`. Ритм между полями перестаёт быть равномерным.
4. **Дефолты сведены в ноль.** `--fforms-control-border-color: currentColor` даёт 1px чистого чёрного, `--fforms-control-border-radius: 0`, фон прозрачный. У `.fforms-submit` тот же gap, что между полями, — нет ступени «группа полей → действие».
5. **Спека уже разошлась с кодом.** В `theming.md` перечислены `--fforms-form-gap: 1.25rem`, `--fforms-control-border-radius: 4px`, `--fforms-textarea-min-height: 10rem`, `--fforms-control-padding: 0.65em 0.8em`; в `style.scss` фактически `1rem`, `0`, `8rem`, `0.7em 0.8em`.

## Составляющие и особенности

**Принципы.** Только `:where()` (нулевая специфичность). Все значения — через существующие публичные переменные; имена из `theming.md` не переименовываются и не удаляются. Никаких цветов, кроме уже объявленных error/success: оттенки выводим из `currentColor`.

**A. Паритет разметки редактора и фронта**

- `EditBuilder`: `useInnerBlocksProps( useBlockProps( { className: 'fforms-fields' } ), { template } )` — контейнер inner blocks получает тот же класс и тот же `gap`, что и на фронте.
- `field.js`: убрать обёртку `.fforms-field-preview`, сделать `.fforms-label` и `.fforms-control` прямыми потомками `.fforms-field` — как в `field_markup()`. Правило для `.fforms-field-preview` в `style.scss` удаляется вместе с ней.

**B. Шкала отступов — три ступени вместо одной**

| Переменная | Было | Стало | Что разделяет |
| --- | --- | --- | --- |
| `--fforms-field-gap` | `0.5rem` | `0.375rem` | label ↔ контрол |
| `--fforms-form-gap` | `1rem` | `1.25rem` | поле ↔ поле |
| `--fforms-submit-gap` | — | `0.5rem` | последнее поле ↔ кнопка (дополнительный `margin-block-start`) |

Тот же `--fforms-submit-gap` отделяет `.fforms-response`. Пустой `.fforms-field-error` скрывается: `:where(.fforms-field-error:empty) { display: none }`.

**C. Дефолты контролов и подписей**

- Рамка: `color-mix(in srgb, currentColor 35%, transparent)` с предшествующим объявлением `currentColor` как fallback для старых браузеров.
- `--fforms-control-border-radius: 4px`, `--fforms-control-padding: 0.65em 0.8em`, `--fforms-textarea-min-height: 6.5rem`.
- `:hover` и `:focus` доводят рамку до `currentColor`; `:focus-visible` outline не трогаем — контракт доступности сохраняется.
- `.fforms-label` / `legend.fforms-label`: `font-weight: 500`, `line-height: 1.3`, `legend { padding-inline: 0 }`.
- `.fforms-submit` остаётся `wp-element-button` и наследует кнопку темы; своих цветов не добавляем.

**D. Синхронизация**

- `assets/fallback-view.css` (dev-fallback при отсутствии `build/`) приводится к тем же значениям.
- `docs/specs/theming.md`: список переменных выравнивается по фактическим дефолтам, добавляется `--fforms-submit-gap`, в «Stable selectors» убирается `.fforms-field-preview`.

## Критерии приемки (checklist)

- [ ] В редакторе `fform` форма из дефолтного шаблона (Name / Email / Message / Send) показывает те же отступы, что и фронтенд: рамки соседних полей не соприкасаются, кнопка визуально отделена от `textarea`.
- [ ] Дерево поля в редакторе и на фронте совпадает: `.fforms-field > .fforms-label + .fforms-control`; класс `.fforms-field-preview` не встречается ни в коде, ни в спеке.
- [ ] Пустой `.fforms-field-error` не занимает места: computed-расстояние от контрола до следующего поля равно `--fforms-form-gap`.
- [ ] Соблюдены три ступени: label↔контрол < поле↔поле < последнее поле↔кнопка.
- [ ] Все новые значения берутся из CSS-переменных; переопределение `--fforms-*` в `:root` темой меняет вид без `!important`.
- [ ] Имена переменных и селекторов, объявленные в `theming.md` как публичный контракт, не изменены и не удалены; новое задокументировано.
- [ ] `theme.json` с `styles.blocks.fforms/form` и `styles.elements.button` по-прежнему перебивает дефолты плагина.
- [ ] Блочная тема (TT5) и классическая тема: форма опрятна без единой настройки — Playwright-скриншоты редактора и фронта в `specs/`.
- [ ] Legacy-форма из `_fforms_schema` и форма, вставленная блоком/шорткодом на страницу, выглядят одинаково.
- [ ] `assets/fallback-view.css` даёт тот же результат при отсутствии `build/`.
- [ ] `npm run build` и lint проходят; `docs/specs/theming.md` обновлён в том же изменении.

## Дорожная карта

1. Паритет разметки: `edit-builder.js` и `field.js` — даёт основной видимый эффект, дальше всё уже видно в редакторе.
2. Пустая ошибка + новая шкала отступов в `style.scss` / `view.scss`.
3. Дефолты контролов и подписей.
4. `assets/fallback-view.css` — те же значения.
5. `docs/specs/theming.md`.
6. Playwright-скриншоты редактора и фронта; сверка блочной и классической темы.

Шаги 2–4 зависят от 1 (иначе результат не проверить глазами в редакторе); 5–6 замыкают изменение.

## Итого и рекомендации

Сначала чинится разметка, потом подбираются значения: шаг 1 убирает большую часть «аляповатости» со скриншота, шаги 2–3 дают читаемую иерархию. Ничего из публичного контракта темизации не ломается — меняются только дефолты, которые тема и так перебивает.

## Открытые вопросы

- Нужен ли нейтральный fallback-вид кнопки для классических тем, где `wp-element-button` не стилизован, — или это уже зона темы?
- `color-mix` требует браузеров 2022+. Достаточно ли двойного объявления с `currentColor` впереди, или оставить `currentColor` дефолтом?
- `--fforms-textarea-min-height` 8rem → 6.5rem: решение по умолчанию или отдать теме без изменения дефолта?
