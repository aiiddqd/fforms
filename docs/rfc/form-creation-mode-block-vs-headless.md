# RFC: Режим формы — Block editor vs Headless API

## Вводные

Новая форма (CPT `fform`) создаётся обычным Gutenberg-сценарием с шаблоном `fforms/form` + поля + `submit`. Режим меняется в боковой панели: **Block editor** сохраняет форму как блок и REST-ресурс, а **Headless API** оставляет её REST-ресурсом с JSON-схемой полей.

## Назначение и цели

Часть форм создаётся только для внешних/headless-фронтендов (см. `use-fforms-as-headlesscms-backend.md` — там это решено для форм, описанных в PHP-коде). Но редакторы без доступа к коду тоже должны иметь возможность завести «REST-only» форму из админки, не разбираясь с блочным конструктором и не рискуя случайно вставить её на страницу как блок. Цель — сохранить привычное быстрое создание формы и дать редактору переключатель режима там, где он настраивает форму.

Заинтересованные стороны: администраторы сайта, создающие формы через wp-admin; разработчики headless-фронтендов, потребляющие REST; ревьюеры UX админки.

Вне объёма: программная регистрация форм через `fforms_add_api_route()` (уже реализована отдельно, не пересекается с этим RFC); визуальный конструктор полей для headless-режима (см. «Альтернативные варианты»).

## Предпосылки
- [x] новая форма по умолчанию создаётся как Block editor;
- [x] в боковой панели можно сменить режим между Block editor и Headless API без потери схемы полей;
- [x] Headless API доступен только через REST API и не отображается в блоках Gutenberg;
- [x] Block editor доступен как блок Gutenberg и через REST API.

## Составляющие и особенности

**Ключевой факт**, упрощающий реализацию: `Schema_Repository::for_form()` уже сегодня умеет читать схему двумя способами — компилировать её из блоков `fforms/form` в `post_content`, либо (если блока нет) брать JSON напрямую из meta `_fforms_schema`. Второй путь уже покрывает REST-контракт (`GET /forms/{id}`, `/schema`, `POST /submit`) без каких-либо изменений. Значит, «headless-режим» — это в первую очередь ограничение **редакторского интерфейса и видимости в блоках**, а не новый формат хранения или новый REST-путь.

1. **Meta-флаг режима.** Новое поле `_fforms_mode` (`block` | `headless`, по умолчанию `block`) регистрируется в `Post_Types::register_meta()`. Все существующие формы получают `block` по умолчанию — обратная совместимость гарантирована.

2. **Создание формы.** `post-new.php?post_type=fform` остаётся стандартным WordPress-сценарием: новая форма получает `block` по умолчанию и текущий шаблон блоков без промежуточного экрана.

3. **Переключатель режима.** `enqueue_form_settings_sidebar()` добавляет в документную панель SelectControl. При переходе в `headless` текущие блоки преобразуются в JSON-схему и заменяются пустым paragraph-блоком через block-editor store, чтобы WordPress не вставил стартовый шаблон повторно; при обратном переходе JSON-схема собирается обратно в `fforms/form` с полями и submit. Некорректная JSON-схема заменяется на стартовую схему, как и на сервере.

4. **Редакторский интерфейс для `headless`.** Блочный шаблон (принудительная вставка `fforms/form` + полей) применяется только для `block`. Для `headless` холст блокируется (`templateLock: 'all'`, пустой template), а `enqueue_form_settings_sidebar()` (уже существующий JS-бандл `assets/form-settings-sidebar.js`) добавляет отдельную панель редактирования полей формы, которая пишет JSON прямо в `_fforms_schema` (санитайзер `Schema::sanitize_json()` уже есть и переиспользуется как есть). Для `block` поведение не меняется.

5. **Запрет встраивания headless-форм как блока.** `Blocks\Form_Renderer::render_reference()` (используется атрибутом `ref`/`formId` блока `fforms/form` для встраивания чужой формы на другую страницу) должен отказывать в рендере, если у формы `_fforms_mode === 'headless'` — так же, как сейчас отказывает для неопубликованной формы. Проверка на сервере обязательна (не только в UI), поскольку атрибуты блока приходят от клиента. Дополнительно UI-пикер формы в инспекторе блока (клиентский компонент выбора `ref`) фильтрует список по полю `mode`, которое добавляется в ответ `GET /forms` и `GET /forms/{id}` рядом с существующим `source`.

6. **REST не меняется по контракту.** `_fforms_mode` не влияет на публичные `GET /forms(/{id})`, `/schema` и `POST /submit` — headless-форма остаётся полноценно доступной через REST независимо от режима. Меняется только видимость в блочном UI.

## Критерии приемки (checklist)

- [x] «Добавить форму» (кнопка в списке, admin bar и прямой `post-new.php?post_type=fform`) сразу открывает стандартный Block editor без промежуточного экрана.
- [x] Переключатель в боковой панели переводит Block editor в Headless API, переносит актуальные поля в `_fforms_schema` и очищает блочный холст.
- [x] Переключатель в боковой панели переводит Headless API в Block editor и собирает из `_fforms_schema` корневой блок с теми же полями.
- [x] У существующих (созданных до фичи) форм `_fforms_mode` читается как `block`, их работа не меняется.
- [x] `GET /fforms/v1/forms` и `GET /fforms/v1/forms/{id}` возвращают поле `mode` для каждой формы.
- [x] `POST /fforms/v1/submit` и чтение схемы работают одинаково для `block` и `headless` форм — режим не влияет на REST-контракт.
- [x] Блок `fforms/form` с `ref`, указывающим на headless-форму, не рендерит её на фронтенде (тот же плейсхолдер, что и для неопубликованной/несуществующей формы), даже если атрибут проставлен вручную через код блока.
- [x] Пикер формы в инспекторе блока `fforms/form` не предлагает headless-формы для выбора через `ref`.
- [ ] `php -l`, `npm run lint:js`, `npm run build` проходят; `docs/specs/base.md` дополнен описанием `_fforms_mode`.

## Дорожная карта

1. `_fforms_mode` в `Post_Types::register_meta()`.
2. Стандартное создание Block editor без специального `post-new.php` flow.
3. Клиентская часть переключения: Block → JSON-схема → Headless и JSON-схема → Block.
4. `mode` в REST-ответах `GET /forms`, `GET /forms/{id}`; фильтрация headless-форм в пикере блока `fforms/form`.
5. Серверная блокировка рендера headless-формы в `render_reference()`.
6. Обновление `docs/specs/base.md`, ручная проверка чек-листа.

Шаги 1–2 блокируют 3; шаги 4 и 5 независимы друг от друга и от шага 3.

## Итого и рекомендации

Не вводить новый формат хранения схемы или отдельный REST-путь под headless-режим — переиспользовать существующую развилку в `Schema_Repository` (блоки vs `_fforms_schema` JSON), которая уже сегодня отдаёт корректный REST-контракт для форм без блока в контенте. Режим меняется рядом с остальными настройками формы, а конвертация сохраняет набор полей. Это сохраняет привычный Gutenberg-сценарий и не требует отдельного экрана.

## Открытые вопросы

- Для headless-режима: что показать в v1 — сырой JSON-textarea поверх `_fforms_schema` (минимум работы, санитайзер уже есть) или repeatable-UI со списком полей (ближе к «интерфейс сильно проще» из предпосылок, но требует новой React-панели)? См. альтернативы ниже.
- Нужно ли на экране выбора режима сразу показывать созданные default-формы (`Default_Forms`) как пример, или ограничиться двумя карточками режима?

### Альтернативные варианты

**Вариант A: сырой JSON-textarea для headless-полей.**
Плюсы: переиспользует готовый `Schema::sanitize_json()`, минимум нового кода и рисков, быстро реализуется.
Минусы: не решает «интерфейс сильно проще» в UX-смысле — редактору без опыта с JSON неудобно; не соответствует духу предпосылок.

**Вариант B: repeatable-UI со списком полей (имя/лейбл/тип/обязательность) в сайдбар-панели.**
Плюсы: полностью закрывает требование «проще»; не требует знания JSON.
Минусы: новая React-панель, больше кода и тестирования на первой итерации.

**Рекомендация:** начать с Варианта A в рамках этого RFC (закрывает функциональные критерии приёмки), Вариант B — отдельным follow-up RFC после обратной связи от пользователей headless-режима.
